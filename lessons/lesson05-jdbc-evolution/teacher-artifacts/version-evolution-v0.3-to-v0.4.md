# 选课系统v0.3到v0.4演化证据

## 1. v0.3基线

第04次课已经运行并验证：学生、课程、教学班、选课、学校、共享协议和学期数据可保存；同一学生在同一学期不能重复选择同一课程；共享协议、合作校配额和总容量可由SQL检查。

## 2. 变化触发器

教务处新增历史重修要求：未通过课程的学生可以在后续学期重修；已通过者能否再次修读由课程策略决定。

课堂并发实验同时提出另一个问题：两个请求可能在插入前都读到最后一个空位。

## 3. v0.3运行缺口

| 运行观察 | v0.3能回答 | v0.3不能回答 |
|---|---|---|
| Enrollment记录学生、课程和学期 | 学生选过什么 | 最终成绩、是否通过 |
| Course保存课程基本信息 | 课程是什么 | 课程采用哪种重修策略 |
| SELECT统计当前人数 | 当前快照是否有空位 | 查询后到插入前是否被其他事务占用 |
| 独立SQL可增删改查 | 单条语句是否成功 | 一次选课的多项检查是否整体提交或回滚 |

## 4. 影响分析

| 层次 | v0.4增量 | 验证方式 |
|---|---|---|
| 需求 | 历史重修、原子选课 | 需求变化说明和验收条件 |
| 模型 | Enrollment增加成绩与通过状态；Course增加重修策略 | PlantUML与迁移脚本 |
| 数据 | 增加历史学期、通过与未通过记录、最后一席场景 | `02_history_seed.sql` |
| 查询 | 多表连接取得学生历史修读事实 | `04_join_query.sql`、Course1 |
| 程序 | 配置、连接、PreparedStatement、Service事务 | Java源码和运行命令 |
| 并发 | 锁定目标教学班后检查余量并写入 | AC-410、AC-411 |
| 验收 | 成功、拒绝、回滚、并发均产生可执行证据 | `run_checks.sh` |

## 5. 固定规则顺序

1. 锁定并检查教学班。
2. 检查学生存在且状态有效。
3. 检查历史重修资格。
4. 检查同一学期重复选课。
5. 检查跨校协议与合作校配额。
6. 检查教学班总容量。
7. 写入选课并提交。

该顺序把历史资格作为主拒绝原因，并与教师代码和验收用例保持一致。

## 6. 保持不变

- 延续v0.3的学生、课程、教学班和学校标识。
- 延续同一学期不能重复选择同一课程的约束。
- 延续共享协议、合作校配额和总容量的语义。
- 延续第04次课的PostgreSQL数据基线，不另建平行模型。

## 7. 版本结论

本次变化同时修改需求、领域模型、数据库数据、查询、程序事务边界、并发策略和验收标准，因此形成v0.4。JDBC负责实现这些变化，本身不构成版本升级依据。
